# 扫码冷却期隔离修复 - 快速测试

## 测试目标

验证不同订单/门店的扫码冷却期和灯条请求是**完全隔离**的，不会互相干扰。

## 测试步骤

### 1. 基础功能测试（单一订单）

1. 打开C端订单详情页（如 `c-order-detail.html?id=DD123456789`）
2. 点击"扫码取件"按钮
3. 验证：
   - 控制台输出 `[C端] 准备灯条请求`
   - M端收到灯条请求并弹窗
4. 再次点击"扫码取件"
5. 验证：控制台输出 `[C端] 灯条请求已触发，跳过重复触发`

**预期**：✅ 灯条请求只能触发一次

### 2. 订单切换测试

1. 完成测试1后（灯条已触发）
2. 切换到**另一个订单**（如 `c-order-detail.html?id=DD987654321`）
3. 点击新订单的"扫码取件"按钮
4. 验证：
   - 控制台输出 `[C端] 准备灯条请求`（不是"已触发跳过"）
   - M端再次收到灯条请求

**预期**：✅ 新订单可以独立触发灯条请求

### 3. 冷却期隔离测试

1. 在订单A点击"扫码取件"（触发冷却期30秒）
2. **不等待**，立即切换到订单B
3. 点击订单B的"扫码取件"按钮
4. 验证：
   - 订单B**应该能正常触发**灯条请求
   - 不应该被订单A的冷却期阻塞

**预期**：✅ 冷却期按订单隔离，互不影响

### 4. 历史订单测试

1. 打开一个**已完成或历史订单**
2. 点击"扫码取件"
3. 验证：新功能正常工作

**预期**：✅ 历史订单也能正确使用防重复机制

### 5. M端去重测试

1. C端订单A扫码，触发灯条请求
2. M端收到请求，弹窗显示
3. 刷新M端页面（不刷新C端）
4. 观察M端：
   - **不应该**再次弹窗显示同一个请求

**预期**：✅ M端正确识别已处理的请求

## 常见问题排查

### Q1: 切换订单后仍然显示"灯条请求已触发跳过"？

**检查**：
1. 打开浏览器控制台
2. 搜索 `orderStateMap`，确认Map中有多个订单记录
3. 检查是否URL监听正常工作

**可能的修复**：检查是否有其他代码重置了 orderId

### Q2: M端重复弹窗？

**检查**：
1. 控制台是否输出 `[M端] 灯条请求已处理过，跳过`
2. 如果没有，检查 `processedLightRequests` Map 是否正确工作

**可能的修复**：检查 localStorage 中是否有残留的 `store_light_request`

### Q3: 冷却期不生效？

**检查**：
1. 冷却期是30秒（30000ms）
2. 检查 `getCurrentCooldownUntil()` 是否返回正确的值
3. 确认 `orderId` 在冷却期检查前已正确设置
